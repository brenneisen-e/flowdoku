Event Creation: Current State & Optimization Requirements

Analysis of the current process and requirements catalog for a dynamic, modular event creation system

This document is also available as a Word file: Download DOCX

Part 1: Current State – What happens during event creation today?

1.1 Overall Process Overview

Event creation goes through two phases: manual input in the Power App and automatic backend processing by Power Automate flows.

Overall Process at a Glance

  1. Organizer opens the app → Navigates to “Create new event”
  2. Selects one of 3 event types (B2Run, JP Morgan, Other Deloitte Event)
  3. Fills out the respective fixed form
  4. Clicks “Submit” → Record is saved to SharePoint list Events
  5. SharePoint trigger fires the main flow NewEventAdded_SiteProvis
  6. Flow automatically creates: Subsite, participant list, Outlook calendar event, notification, permissions

All three forms use the same logic:

Submit button only becomes active when all required fields are filled (DisplayMode check on IsBlank/IsEmpty).

On Submit click:

  4. Notify("The event has been created successfully...") – Success notification

1.3 Phase 2: Automatic Backend Processing (Power Automate)

1.3.1 Main Flow: NewEventAdded_SiteProvis

Automatically triggered by SharePoint trigger “When an item is created” on the Events list (check interval: 1 minute). Consists of 25 actions in 6 clusters:

ClusterWhat happensTechnical details
1. Initialization Event status is set to “Under Construction”, 6 workflow variables are initialized SharePoint PatchItem + 5x InitializeVariable (varSiteTitle, varSiteURL, varSubject-Name, varFinalURL, varContentTypeName)
2. URL Sanitization Event title is cleaned of special characters for a valid SharePoint URL Compose creates filter array (spaces, :, #, %, ", *, ?, /, \, |), Foreach loop removes each character iteratively
3. Create Subsite A dedicated SharePoint subsite is created for the event HTTP POST to /_api/web/webinfos/add with Template STS#3 (Team Site). Response is parsed for ServerRelativeUrl
4. Apply Template Participant list with the appropriate column schema is created Switch on Content Type → Child Flow ApplyTemplateB2Run or ApplyTemplateOtherEvent
5. Outlook Calendar Event Calendar event in shared mailbox is created (basis for later participant invitations) Child Flow CreateOutlookEventSharedMailbox. Returned Outlook Event ID is stored in Events list. URL gets /Lists/Teilnehmerliste appended
6. Notification & Permissions Organizer receives confirmation email with link. If audience is defined, access permissions are set Load logos (Data-URI), Foreach over Organizer → Email from shared mailbox. Condition checks Audience Mail → Child Flow EventPermission

1.3.2 Child Flow: ApplyTemplateB2Run

Receives the subsite URL and creates the participant list via SharePoint REST API:

  1. POST to /_api/web/lists → creates list “Teilnehmerliste” (Template 100)
  2. Individual HTTP requests create fields: Teilnehmername, Email, Status (Choice: Registered/Waitlist/Cancelled), Nr, CheckIn
  3. 7 free text fields (Freitextfeld1–7) are always created
  4. Default view is retrieved, success is confirmed

1.3.3 Child Flow: ApplyTemplateOtherEvent

Identical structure to ApplyTemplateB2Run. Creates the same base and free text fields. Separate flow for potential future differentiation.

1.3.4 Child Flow: CreateOutlookEventSharedMailbox

Receives event details (title, description, start, end, location) → creates Outlook calendar entry via Office 365 Connector → returns Event ID.

1.3.5 Child Flow: EventPermission

Only called when Audience Mail is set:

  1. Remove existing sharing permissions
  2. Audience group receives read access
  3. Organizer receives full access

Part 2: Identified Problems

P1: Rigid, triple-duplicated forms

There are 3 separate form screens (B2Run: ~1,900 lines YAML, Other: ~3,500 lines, JP Morgan: ~1,200 lines) with significant overlap. Any change to shared fields must be replicated across all three forms.

P2: 4x effort for field extensions

When a new field is needed (e.g. “Dietary Requirements”), it must be adapted in 4 places:

  1. Event creation form in the Power App (add DataCard)
  2. Event creation flow (template flow must create column in participant list)
  3. Registration form in the Power App (participants must see and fill in the field)
  4. Registration flow (RegisterParticipant must write the field to the participant list)

P3: Overloaded participant list

Every event receives all possible columns in the participant list – even if it is a small company party that only needs name and email. This leads to cluttered lists with many empty columns.

P4: No preview of registration page

The organizer cannot see during event creation how the registration page will look for participants. Configuration errors only become apparent when participants try to register.

P5: No post-creation editing

Once created, events cannot be modified through the app. If an additional field is needed or the maximum number of participants changes, this must be changed manually in SharePoint.

P6: Two nearly identical template flows

ApplyTemplateB2Run and ApplyTemplateOtherEvent have the same structure and create the same fields. Maintaining two flows for effectively the same logic unnecessarily increases maintenance effort.

Part 3: Requirements Catalog – Dynamic Event Creation

3.1 Target Architecture Overview

Current State

  • 3 fixed forms
  • 2 template flows
  • Always all columns in participant list
  • No preview
  • No post-creation editing
  • 4x change effort

Target State

  • 1 dynamic form with menu card principle
  • 1 universal template flow with dynamic column list
  • Participant list with only required columns
  • Live preview of registration page
  • Events editable after creation
  • 1x change effort (field configuration controls everything)

3.2 Detailed Requirements

  • Dynamic Form with Menu Card Principle High

    The existing system of 3 fixed forms is replaced by a single, dynamic form. The organizer initially sees only the base fields (title, organizer, date, description, max. participants, event image). Below that is a section “Add more fields” with a menu card.

    Menu card: Available field modules are displayed as tiles/chips. Clicking “+” adds the module to the form. Examples of modules:

    • T-shirt size (with configurable options)
    • Allergies / dietary preferences
    • Hotel booking (single/double room, location)
    • Running track / start block (for running events)
    • Custom free text field (question freely definable)
    • Custom dropdown (question + options freely definable)
    • Audience restriction

    Added modules appear in the form and can be removed by clicking “×”.

  • Field Configuration as Data Model High

    The selected fields/modules are stored as a structured configuration (e.g. as JSON string or in a separate SharePoint list EventFieldConfig). This configuration is the Single Source of Truth and controls:

    • Which columns are created in the participant list (event creation flow)
    • Which fields are displayed in the registration form
    • Which fields the registration flow writes to the participant list

    This eliminates the 4x change effort. A new field module only needs to be defined once as a template.

  • Dynamic Participant List (only required columns) High

    The template flow (new: a single universal flow, replaces ApplyTemplateB2Run and ApplyTemplateOtherEvent) reads the field configuration of the event and creates the participant list only with the columns that were actually configured.

    Always created (base columns): Participant name, Email, Status, Nr, CheckIn, Salutation, First name, Last name

    Only when configured: HotelRequired, RoomType, TShirtGroesse, Allergies, FoodPreferences, FreeTextField1–n, DropdownField1–n, etc.

    Column name synchronization: The column names in the SharePoint participant list must exactly match the labels assigned by the organizer. If the organizer names a field e.g. “Travel Expenses”, the corresponding column in the participant list must also be called “Travel Expenses” – not a technical or deviating name.

  • Live Preview of Registration Page High

    During event creation, the organizer sees in a preview panel (e.g. right side or lower area) how the registration form will look for participants. The preview updates in real-time when modules are added or removed.

    This includes:

    • All visible fields in the order participants will see them
    • Required field markers
    • Dropdown options (when defined)
    • Info texts / help texts for fields
  • Post-Creation Event Editing High

    Organizers can open and edit existing events through the app:

    • Modify base data: Title, date, max. participants, description, etc.
    • Add fields: New modules can be added to the event even after creation. The flow then creates the missing column(s) in the existing participant list.
    • Remove fields: Only possible if no data exists in the column yet (or with a warning). Alternatively, the column is only hidden but not deleted.

    Note: When columns are added after the fact, already registered participants will have no value there – this must be handled cleanly in the app / view.

  • Universal Template Flow (Consolidation) Medium

    The two existing flows ApplyTemplateB2Run and ApplyTemplateOtherEvent are merged into a single flow. It receives as parameters:

    • Subsite URL
    • Field configuration (which columns to create, including type and optional choice options)

    The flow dynamically iterates over the configuration and creates only the defined columns.

  • Dynamic Registration Form (Participant Side) High

    The registration form for participants is also generated dynamically from the event’s field configuration. Participants only see the fields that were configured for this specific event.

    Similarly, the RegisterParticipant flow must read the configuration and write only the relevant fields to the participant list.

  • Clean, Intuitive UI Design Medium — TO BE COORDINATED WITH PROJECT TEAM GERMANY

    The new form should be clear and intuitive:

    • Clear grouping: base information at top, optional modules below
    • Menu card with categories (e.g. “Catering”, “Accommodation”, “Sports”, “Custom”)
    • Visual feedback when adding/removing modules
    • Responsive design for mobile use
    • Preview panel clearly separated (e.g. as side panel or tab)
  • Event Templates / Quick Start Nice-to-have — TO BE COORDINATED WITH PROJECT TEAM GERMANY

    Pre-defined templates for common event types (e.g. “Running event”, “Company party”, “Conference”) that can be selected at the start and pre-populate the form with typical modules. The organizer can still add or remove modules afterwards.

  • Backward Compatibility Medium

    Existing events (created with the old system) must continue to function. The Events list and existing participant lists must not be damaged. Ideal: A migration mechanism that retroactively provides existing events with a field configuration.

Part 4: Target State Architecture Sketch

4.1 Event Creation Process (New)

  1. Organizer opens app → Clicks “Create new event”
  2. Optional: Select template (B2Run, Company party, Blank, ...) → Form is pre-populated
  3. Fill in base fields (title, organizer, date, max. participants, description, image)
  4. Add modules from menu card via “+” click:
    • e.g. + T-Shirt → Configuration: Which sizes?
    • e.g. + Hotel → Configuration: Single room only? Location?
    • e.g. + Free text field → Input: Question + info text
  5. Check preview: Registration page is displayed live in the preview panel
  6. Submit: Event + field configuration are saved
  7. Flow is triggered:
    • Create subsite (as before)
    • Universal template flow reads field configuration → creates only required columns
    • Create Outlook calendar event (as before)
    • Notification + permissions (as before)

4.2 Participant Registration Process (New)

  1. Participant opens event in the app
  2. App reads the event’s field configuration
  3. Registration form is dynamically generated – only the configured fields
  4. Participant fills in and clicks “Register”
  5. RegisterParticipant flow reads configuration and writes only relevant fields

4.3 Post-Creation Event Editing Process (New)

  1. Organizer opens existing event in the app
  2. Form loads in edit mode with existing configuration
  3. Organizer can modify base data and add/remove modules
  4. On “Save”: Flow checks delta (new columns? removed columns?) and adjusts participant list
  5. Outlook calendar event is updated if needed

4.4 New Data Model (Draft)

ComponentDescription
Events list (adapted) Contains only base fields + a column FieldConfig (JSON string or reference to config list). All event-type-specific “visible” toggle columns are eliminated.
FieldConfig (new) Stores per event which modules/fields are active. Possible structure:
[{"module": "tshirt", "options": ["S","M","L","XL"], "required": true}, {"module": "freetext", "label": "Allergies?", "info": "Please specify"}, ...]
Participant list (dynamic) Individually composed per event. Only base columns + the columns derived from FieldConfig.
